# User Service

Микросервис для работы с пользователями и связанными с ними данными.

## О проекте

User Service — учебный backend-микросервис, разработанный на Java и Spring Boot.

Основной целью проекта была практика **реализации бизнес-логики на основе требований**, а также работа с сервисным слоем, JPA-сущностями, DTO и связанными сущностями.

В процессе разработки бизнес-требования последовательно преобразовывались в:

- алгоритм выполнения операции;
- проверки бизнес-условий;
- обработку ошибок;
- работу с сущностями и их связями;
- сохранение изменений в базе данных.

Особое внимание уделялось не только написанию кода, но и самостоятельному анализу требований перед реализацией.

---

## Основные возможности

В микросервисе реализованы операции, связанные с:

- пользователями;
- целями;
- приглашениями пользователей в цели;
- образованием;
- карьерой;
- рабочим графиком;
- навыками;
- предложениями навыков;
- другими связанными пользовательскими данными.

Реализованная бизнес-логика включает:

- проверку существования сущностей;
- проверку прав пользователя на выполнение операции;
- проверку принадлежности пользователя к цели;
- проверку ролей пользователя в цели;
- проверку ограничений бизнес-правил;
- проверку временных диапазонов;
- проверку количества активных целей;
- проверку повторного присоединения к цели;
- обработку различных сценариев принятия и отклонения приглашений.

## Архитектура

Проект построен с разделением ответственности между основными слоями:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
PostgreSQL
```

### Controller

Отвечает за:

- получение HTTP-запросов;
- получение параметров и данных запроса;
- передачу данных в сервисный слой;
- формирование HTTP-ответа.

### Service

Содержит основную бизнес-логику приложения.

Именно на уровне Service выполняются:

- проверки бизнес-правил;
- проверки прав пользователя;
- проверки связанных сущностей;
- работа с несколькими сущностями;
- изменение состояния сущностей;
- принятие решений в зависимости от условий.

### Repository

Отвечает за взаимодействие с базой данных через Spring Data JPA.

### Entity

JPA-сущности описывают данные, хранящиеся в PostgreSQL, и связи между сущностями.

### DTO

DTO используются для передачи данных между API и сервисным слоем.

Для различных операций используются отдельные DTO, например для создания и обновления данных.

### Mapper

MapStruct используется для преобразования между DTO и Entity.

```text
DTO → Entity
Entity → DTO
```

## Подход к реализации бизнес-логики

Одной из основных целей проекта было научиться переводить текстовое бизнес-требование в последовательный алгоритм действий.

Перед написанием кода задача разбиралась следующим образом:

```text
Бизнес-требование
        ↓
Определение условий
        ↓
Построение алгоритма
        ↓
Проверка граничных случаев
        ↓
Реализация на Java
        ↓
Проверка результата
```

Основной принцип разработки:

> Сначала понять, что должна делать система, затем описать алгоритм и только после этого писать код.

Это позволило уделять внимание не только синтаксису Java и Spring, но и правильной реализации поведения системы.

## Реализованная бизнес-логика

### Приглашения в цель

Реализованы сценарии:

- создание приглашения;
- принятие приглашения;
- отклонение приглашения.

При создании приглашения проверяется:

- нельзя пригласить самого себя;
- приглашённый пользователь не должен уже участвовать в цели;
- приглашённый пользователь не должен быть ментором цели;
- пользователь, создающий приглашение, должен иметь отношение к цели.

При принятии приглашения проверяется:

- приглашение существует;
- текущий пользователь является адресатом приглашения;
- пользователь ещё не находится в цели;
- количество активных целей пользователя соответствует установленному ограничению.

При отклонении приглашения проверяется:

- приглашение существует;
- текущий пользователь является адресатом приглашения.

---

### Образование

Реализованы операции:

- добавление образования;
- получение образования;
- обновление образования.

При создании и обновлении проверяется, что год начала обучения не находится в будущем.

При обновлении дополнительно проверяется, что пользователь изменяет собственные данные.

---

### Карьера

Реализованы операции:

- добавление информации о карьере;
- получение информации о карьере;
- обновление информации о карьере.

При создании и обновлении проверяется, что дата начала работы не находится в будущем.

При обновлении проверяется, что пользователь изменяет собственные данные.

---

### Рабочий график

Реализованы операции:

- создание рабочего графика;
- получение рабочего графика;
- обновление рабочего графика.

Проверяются следующие бизнес-правила:

- начало рабочего дня должно быть раньше его окончания;
- начало обеда должно быть раньше окончания обеда;
- обед должен полностью находиться внутри рабочего дня.

Пример корректного графика:

```text
09:00 ───────────────────────── 18:00
          12:00 ───── 13:00
              обед
```

Пример некорректного графика:

```text
09:00 ───────────────────────── 18:00
     08:00 ───── 10:00
```

В данном случае обед начинается раньше рабочего дня.

## Проверка прав пользователя

Для операций, которые должны выполняться от имени текущего пользователя, используется контекст пользователя.

Общий принцип:

```text
HTTP-запрос
     ↓
UserContext
     ↓
ID текущего пользователя
     ↓
UserRepository
     ↓
User
     ↓
Проверка прав
```

Например, при обновлении образования, карьеры или рабочего графика проверяется принадлежность записи текущему пользователю.

Упрощённо проверка выглядит следующим образом:

```text
ID владельца записи
        ==
ID текущего пользователя
```

Если идентификаторы не совпадают, операция не выполняется.

## Валидация

Для проверки входных данных используется Bean Validation.

Пример:

```java
@NotBlank
private String firstName;
```

Валидация входных данных используется для проверки корректности данных, которые поступают от клиента.

При этом важно разделять:

### Валидацию входных данных

Например:

```text
Поле не должно быть пустым
Поле должно иметь допустимый размер
Значение не должно быть null
```

### Бизнес-логику

Например:

```text
Пользователь не может принять приглашение,
если у него 3 или более активных целей.
```

Такие правила проверяются на уровне Service.

## Обработка ошибок

В бизнес-логике предусмотрена обработка ситуаций, при которых операция не может быть выполнена.

Примеры:

```text
Пользователь не существует
Цель не существует
Приглашение не существует
Пользователь не имеет отношения к цели
Нельзя пригласить самого себя
Пользователь уже находится в цели
Пользователь не является адресатом приглашения
Дата начала работы находится в будущем
Год начала обучения находится в будущем
Обед находится за пределами рабочего дня
```

Ошибки бизнес-логики отделяются от основной логики успешного выполнения операции.

## Работа с DTO и Entity

В проекте DTO используются для отделения API-моделей от JPA-сущностей.

Общий поток данных:

```text
HTTP Request
     ↓
Request DTO
     ↓
Service
     ↓
Entity
     ↓
Repository
     ↓
PostgreSQL
```

При получении данных:

```text
PostgreSQL
     ↓
Entity
     ↓
Service
     ↓
Response DTO
     ↓
HTTP Response
```

Для преобразований используется MapStruct.

## Работа с Optional

При получении сущностей из Repository учитывается ситуация, когда запись может отсутствовать.

Например:

```java
userRepository.findById(userId)
        .orElseThrow(() -> new RuntimeException("Пользователь не существует"));
```

Таким образом, отсутствие сущности рассматривается как отдельный сценарий, который должен быть обработан.

---

## Работа с коллекциями и Stream API

В некоторых бизнес-операциях необходимо проверить наличие пользователя среди участников цели.

Например:

```java
goal.getUsers().stream()
        .anyMatch(user -> user.getId().equals(userId));
```

Такой подход используется для проверки условий над коллекциями связанных сущностей.

Например:

```text
Есть ли пользователь среди участников цели?
        ↓
     anyMatch
        ↓
    true / false
```

## Граничные случаи

При реализации бизнес-логики учитывались не только обычные сценарии, но и граничные случаи.

### Рабочий график

```text
09:00 → 18:00
```

Корректно.

```text
18:00 → 09:00
```

Некорректно.

```text
09:00 → 18:00
08:00 → 10:00
```

Некорректно, потому что обед выходит за пределы рабочего дня.

### Количество активных целей

Если пользователь может иметь менее трёх активных целей:

```text
0 → можно
1 → можно
2 → можно
3 → нельзя
4 → нельзя
```

Такие граничные значения отдельно учитываются при реализации условий.

## Последовательность разработки задачи

Каждая бизнес-задача разбиралась примерно по следующей схеме:

### 1. Требование

Определяется, что именно должна делать система.

### 2. Условия

Из требования выделяются все ограничения и проверки.

### 3. Алгоритм

Условия преобразуются в последовательность действий.

### 4. Реализация

Алгоритм реализуется с использованием Java и Spring.

### 5. Проверка

Проверяются:

- успешный сценарий;
- ошибочные сценарии;
- граничные значения;
- различные комбинации условий.

Такой подход позволяет сначала разобраться в логике задачи, а затем переходить к написанию кода.

User Service — это учебный проект, основной фокус которого находится на **практике бизнес-логики**.

В процессе разработки отрабатывается переход:

```text
"Что требует бизнес?"
        ↓
"Какие условия должны выполняться?"
        ↓
"Что произойдёт при нарушении условия?"
        ↓

```

Главная задача проекта — не просто написать работающий код, а научиться самостоятельно понимать требования и превращать их в корректную реализацию backend-логики.
